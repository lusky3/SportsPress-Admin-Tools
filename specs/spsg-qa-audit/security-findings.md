## Executive Summary

The plugin has a **solid security foundation**: all 23 AJAX handlers have both nonce verification and capability checks, the REST API uses a centralized permission callback, input sanitization is thorough via a dedicated `SPSG_Configuration_Sanitizer` class, and the JavaScript uses an `escHtml()` helper for dynamic HTML. File upload handling includes size limits, extension checks, and path traversal protection.

**Critical findings: 0** — No remotely exploitable vulnerabilities found.
**High findings: 1** — Nonce field name mismatch (functional bug, not exploitable due to WordPress fallback behavior).
**Medium findings: 5** — Missing `wp_unslash()`, unescaped `printf()` output, missing REST arg declarations, exported files accessible via URL guessing.
**Low findings: 5** — Inconsistent ABSPATH guards, missing `wp_unslash()` on non-string values, REST `replacement_id`/`delete` params lack `sanitize_callback`.

## HIGH Severity

### H-1: AJAX Nonce Field Name Mismatch Between JS and PHP

**Files:**
- `assets/js/schedule-generator.js` (all AJAX calls)
- `assets/js/admin-ui.js` (all AJAX calls)
- `includes/class-admin-ajax.php` (all handlers)

**Description:**
JavaScript sends the nonce value under the field name `nonce`, but PHP checks for field name `spsg_nonce`:

```javascript
// JS (schedule-generator.js:37-43)
$.ajax({
    url: ajaxurl,
    type: 'POST',
    data: {
        action: 'spsg_get_export_formats',
        nonce: spsgData.nonces.get_export_formats  // field name: "nonce"
    },
```

```php
// PHP (class-admin-ajax.php, every handler)
check_ajax_referer( 'spsg_get_export_formats', 'spsg_nonce' );  // expects field: "spsg_nonce"
```

**Impact:** This works only because `check_ajax_referer()` falls back to checking the HTTP `Referer` header when the named field is not found in `$_REQUEST`. This means:
1. CSRF protection relies entirely on the Referer header, which is weaker than nonce-in-body verification.
2. Browsers that strip Referer headers (privacy extensions, certain corporate proxies) will cause all AJAX calls to fail with a nonce error.
3. The nonce values generated by `wp_localize_script` are transmitted to the client but never actually verified server-side (the field name doesn't match).

**Affected handlers:** All 23 AJAX handlers in `class-admin-ajax.php`.

**Recommended fix:** Change the JS field name from `nonce` to `spsg_nonce` in all AJAX calls:

```javascript
// Fix in both schedule-generator.js and admin-ui.js
data: {
    action: 'spsg_get_export_formats',
    spsg_nonce: spsgData.nonces.get_export_formats  // match PHP expectation
},
```

## MEDIUM Severity

### M-1: Unescaped `printf()` Output in Renderer — Playing Days

**File:** `includes/class-admin-renderer.php`, line 906

```php
<li><?php printf( __( 'Playing days: %s', 'sportspress-schedule-generator' ), implode( ', ', $config->playing_days ?: array() ) ); ?></li>
```

**Description:** The `%s` placeholder outputs the result of `implode()` on `playing_days` without escaping. While `playing_days` values come from a sanitized configuration (via `sanitize_text_field`), the output is not escaped at the point of rendering. If a stored XSS payload were injected into the configuration data (e.g., via direct database manipulation or a future code path that bypasses sanitization), it would execute here.

**Impact:** Stored XSS if configuration data is compromised. Low practical risk since data passes through `sanitize_text_field` on save, but violates defense-in-depth.

**Also affected:**
- Line 896-899: `printf()` with `season_start`/`season_end` date format output (safe — `DateTime::format()` returns clean strings)
- Line 903-905: `printf()` with `%d` format specifiers (safe — integers)

**Recommended fix:**
```php
<li><?php printf( esc_html__( 'Playing days: %s', 'sportspress-schedule-generator' ), esc_html( implode( ', ', $config->playing_days ?: array() ) ) ); ?></li>
```

### M-2: Missing `wp_unslash()` on `$_POST` String Values

**File:** `includes/class-admin-ajax.php`, multiple lines

**Description:** Several `$_POST` values are passed to `sanitize_text_field()` without first calling `wp_unslash()`. WordPress adds magic-quote-style slashes to all superglobals. Without `wp_unslash()`, values containing apostrophes or backslashes will have extra escaping.

**Affected lines:**
```php
// Line 115
$config_id = sanitize_text_field( $_POST['config_id'] ?? '' );

// Line 161
$config_id = isset( $_POST['config_id'] ) ? sanitize_text_field( $_POST['config_id'] ) : '';

// Line 296
$config_id = sanitize_text_field( $_POST['config_id'] ?? '' );

// Line 320-321
$config_id = sanitize_text_field( $_POST['config_id'] ?? '' );
$new_name = sanitize_text_field( $_POST['new_name'] ?? '' );

// Line 419
$preset_name = sanitize_text_field( $_POST['preset_name'] ?? '' );

// Line 452
$config_id = sanitize_text_field( $_POST['config_id'] ?? '' );

// Line 858, 886
$config_id = sanitize_text_field( $_POST['config_id'] ?? '' );
```

**Impact:** Configuration names containing apostrophes (e.g., "Friday Night's League") will be stored with extra backslashes. Not a security vulnerability per se, but a data integrity issue that violates WordPress coding standards.

**Note:** Line 365 correctly uses `wp_unslash()`:
```php
$json_data = wp_unslash( $_POST['config_data'] ?? '' );
```
And line 753 correctly uses it:
```php
$schedules = map_deep( wp_unslash( $_POST['schedules'] ?? array() ), 'sanitize_text_field' );
```

**Recommended fix:**
```php
$config_id = sanitize_text_field( wp_unslash( $_POST['config_id'] ?? '' ) );
$new_name = sanitize_text_field( wp_unslash( $_POST['new_name'] ?? '' ) );
```

### M-3: REST `/publish` Endpoint — Unregistered Parameters Used Without Sanitization

**File:** `includes/class-rest-api.php`, lines 673-684

**Description:** The `/publish` endpoint registers only `schedule_id` in its `args` array, but the callback uses several additional parameters without declaring them in the route registration:

```php
// These params have no sanitize_callback or validate_callback in route registration:
$offset = (int) ( $request->get_param( 'offset' ) ?? 0 );
$limit  = min( 200, max( 1, (int) ( $request->get_param( 'limit' ) ?? 50 ) ) );
$cr     = in_array( $request->get_param( 'conflict_resolution' ), array( 'skip', 'overwrite' ), true ) ? ... : 'skip';
$status = in_array( $request->get_param( 'event_status' ), array( 'publish', 'draft', 'pending', 'future' ), true ) ? ... : 'publish';
$dry    = (bool) $request->get_param( 'dry_run' );
// Line 682:
'season_id' => (int) $request->get_param( 'season_id' ),
'league_id' => (int) $request->get_param( 'league_id' ),
```

**Impact:** While the callback does cast values to `(int)` and uses `in_array()` whitelisting (which is safe), the lack of declared args means:
1. No automatic sanitization by the REST framework
2. No validation errors for invalid input — silently falls back to defaults
3. Inconsistent with the rest of the API's arg declaration pattern

**Recommended fix:** Add all parameters to the route's `args` array with proper `sanitize_callback` and `validate_callback`.

### M-4: REST `/placeholders/{id}/replace` — Missing `sanitize_callback` for Body Params

**File:** `includes/class-rest-api.php`, lines 45-52, 554-557

**Description:** The route only declares `id` in its args. The `replacement_id` and `delete` parameters used in the callback have no `sanitize_callback`:

```php
// Route registration (line 45-52) — only 'id' declared
'args' => array(
    'id' => array(
        'sanitize_callback' => 'absint',
        'validate_callback' => function( $val ) { return is_numeric( $val ) && (int) $val > 0; },
    ),
),

// Callback (line 554-557) — uses undeclared params
public function spsg_replace_placeholder( $request ) {
    return rest_ensure_response( SPSG_Placeholder_Team_Manager::replace_team(
        (int) $request['id'],
        (int) $request->get_param( 'replacement_id' ),  // no sanitize_callback
        (bool) $request->get_param( 'delete' )           // no sanitize_callback
    ) );
}
```

**Impact:** The `(int)` and `(bool)` casts provide basic type safety, but `replacement_id` should be validated as a positive integer (like `id` is). A value of `0` or negative would pass through silently.

**Recommended fix:**
```php
'args' => array(
    'id' => array( 'sanitize_callback' => 'absint', 'validate_callback' => ... ),
    'replacement_id' => array( 'required' => true, 'sanitize_callback' => 'absint', 'validate_callback' => function( $val ) { return is_numeric( $val ) && (int) $val > 0; } ),
    'delete' => array( 'sanitize_callback' => 'rest_sanitize_boolean', 'default' => true ),
),
```

### M-5: Export Files Accessible via URL Guessing

**File:** `includes/class-export-manager.php`, lines 38-60; `includes/exporters/class-csv-exporter.php`, line 25

**Description:** Exported files are saved to `wp-content/uploads/spsg-exports/` with predictable filenames:

```php
$filename = 'schedule_' . wp_date( 'Y-m-d_H-i-s' ) . '.csv';
// or
$filename = 'schedule-' . wp_date( 'Y-m-d-His' ) . '.xlsx';
```

The export directory has `.htaccess` protection (Apache only) and `index.php`/`index.html` files to prevent directory listing. However:

1. **Nginx servers are not protected** — the `.htaccess` rules don't apply. The code comments acknowledge this but the fix requires manual server configuration.
2. **Filenames are timestamp-based** — an attacker who knows the approximate export time could brute-force the filename (1-second resolution = ~86,400 attempts per day).
3. **Files are never cleaned up** — old exports accumulate indefinitely.

**Impact:** Schedule data (team names, game dates, venues) could be accessed by unauthenticated users on Nginx servers. The data is not highly sensitive (it's sports schedules), but it may contain information the admin hasn't published yet.

**Recommended fix:**
1. ✅ DONE (`fe3d145`) — random token added to filenames: `'schedule_' . wp_date('Y-m-d_H-i-s') . '_' . bin2hex(random_bytes(8)) . '.csv'`
2. ❌ REMAINING — serve exports through a WordPress handler that checks capabilities instead of direct file URLs
3. ✅ DONE (`fe3d145`) — WP-Cron cleanup routine (`spsg_cleanup_export_files`) deletes old exports

## LOW Severity

### L-1: `wp_die()` vs `exit` Inconsistency in ABSPATH Guards

**Files:** Multiple files in `includes/`

**Description:** Most files use `wp_die()` for the ABSPATH guard, but two use `exit`:
- `class-configuration-manager.php`: `exit;`
- `class-statistics-calculator.php`: `exit;`
- `class-rest-api.php`: `exit;`

**Impact:** Purely cosmetic inconsistency. When accessed directly (outside WordPress), `wp_die()` is undefined and would cause a fatal error anyway, so `exit` is actually more correct for this guard. However, the inconsistency suggests copy-paste drift.

**Recommended fix:** Standardize on `exit;` for all ABSPATH guards (it's the more correct choice since `wp_die()` requires WordPress to be loaded).

### L-2: `$_POST['venue_mapping']` and `$_POST['new_venues']` Missing `wp_unslash()`

**File:** `includes/class-admin-ajax.php`, lines 754-755

```php
$venue_mapping = array_map( 'sanitize_text_field', $_POST['venue_mapping'] ?? array() );
$new_venues = array_map( 'sanitize_text_field', $_POST['new_venues'] ?? array() );
```

**Impact:** Same as M-2 — venue names with apostrophes will have extra backslashes. Lower severity because venue names rarely contain special characters.

**Recommended fix:**
```php
$venue_mapping = array_map( 'sanitize_text_field', wp_unslash( $_POST['venue_mapping'] ?? array() ) );
$new_venues = array_map( 'sanitize_text_field', wp_unslash( $_POST['new_venues'] ?? array() ) );
```

### L-3: `imported_data` JSON Decode Uses `stripslashes()` Instead of `wp_unslash()`

**File:** `includes/class-admin-ajax.php`, line 162

```php
$imported_data = isset( $_POST['imported_data'] ) ? json_decode( stripslashes( $_POST['imported_data'] ), true ) : array();
```

**Impact:** `stripslashes()` and `wp_unslash()` are functionally equivalent for strings, but `wp_unslash()` is the WordPress-standard function and handles arrays recursively. Using `stripslashes()` directly works but is inconsistent with WordPress coding standards.

**Recommended fix:**
```php
$imported_data = isset( $_POST['imported_data'] ) ? json_decode( wp_unslash( $_POST['imported_data'] ), true ) : array();
```

### L-4: REST `save_draft()` Bypasses Full Validation

**File:** `includes/class-rest-api.php`, lines 175-210

**Description:** The `save_draft()` method intentionally bypasses full validation to allow partial/draft saves. This is documented with a comment. The method does apply sanitization via `SPSG_Configuration_Sanitizer`. This is an acceptable design decision for a wizard-style UI, but it means invalid configurations can be persisted.

**Impact:** No security impact — the data is sanitized. Invalid configurations will fail at generation time when full validation runs. This is noted for completeness.

### L-5: REST `spsg_venue_csv_parse` MIME Type Check Has OR Fallback

**File:** `includes/class-rest-api.php`, line 428

```php
if ( ! in_array( $mime, $allowed_types, true ) && ! str_ends_with( strtolower( $file['name'] ), '.csv' ) ) {
```

**Description:** The MIME check uses AND logic — if the MIME type doesn't match BUT the filename ends in `.csv`, the file is accepted. This means a file with any content (e.g., PHP code) could pass if named `malicious.csv`. However, since the file is only read with `fgetcsv()` and never executed or moved to a web-accessible location, this is not exploitable.

**Impact:** No practical security impact. The file is parsed as CSV data and the temp file is cleaned up by PHP. Noted for defense-in-depth.

## Positive Findings (What's Done Well)

### ✅ All 23 AJAX Handlers Have Nonce + Capability Checks
Every handler calls `check_ajax_referer()` and `current_user_can('manage_options')` before processing.

### ✅ Centralized REST API Permission Callback
All REST routes use `'permission_callback' => array( $this, 'check_manage_permission' )` which checks `current_user_can('manage_options')`.

### ✅ Dedicated Configuration Sanitizer
`SPSG_Configuration_Sanitizer` provides thorough, type-aware sanitization for all configuration fields including nested arrays, dates, time slots, and enum values.

### ✅ JavaScript Uses `escHtml()` Helper Consistently
Both JS files define and use an `escHtml()` function (`$('<div/>').text(str).html()`) for all dynamic HTML construction. The change history table, home venue preferences, venue import dialog, and generic teams summary all escape user-derived data.

### ✅ CSV File Upload Has Multiple Protections
- 1MB size limit
- Extension check (`.csv` only)
- MIME type verification via `wp_check_filetype()`
- Path traversal protection via `realpath()` + allowed directory check in `SPSG_Venue_Schedule_Importer::parse_csv()`

### ✅ Export Directory Protection
`.htaccess` deny-all rules, `index.php` silence file, and `index.html` empty file prevent directory listing on Apache.

### ✅ No SQL Injection Vectors Found
No raw `$wpdb` queries in the audited files. All database operations go through WordPress APIs (`get_option`, `update_option`, `get_posts`, `get_terms`).

### ✅ All Files Have ABSPATH Guards
Every PHP file checks `defined('ABSPATH')` to prevent direct access.

### ✅ REST API Route Args Use `sanitize_callback` and `validate_callback`
Most route parameters have proper sanitization and validation declared at the route level.
